Before you start

Create the accounts first, then generate every secret in one go — several phases need the same values, and generating them twice is the most common way to end up with a deployment that half-works.

Resend or SMTPEmail + report attachments — optionalfree tier

  1. Generate every secret now. Keep the output somewhere you can paste from for the next 30 minutes.

    # SESSION_SECRET
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"

# TOKEN_ENCRYPTION_KEY — must be exactly 64 hex chars
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# REALTIME_SECRET — only if you're doing phase 06
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# VAPID keypair for web push
npx web-push generate-vapid-keys

  2. Enable Google Sheets API and Google Drive API in your Google Cloud project (APIs & Services → Library).

  3. Provision the Hetzner VM and install Docker. You'll SSH into it in phase 05.

Costly mistake #1

TOKEN_ENCRYPTION_KEY must be identical on the Vercel API and the VM worker. The API encrypts each user's Google refresh token with it; the worker decrypts the same token to poll. A mismatch doesn't fail loudly — every sheet just starts reporting an authorization error.

01 Neon dashboard

Neon Postgres

You need two connection strings from the same database. They are not interchangeable.

WhichLooks likeUsed by
Pooled…-pooler.<region>.aws.neon.tech/…the Vercel API
Direct…<region>.aws.neon.tech/…the VM worker, and prisma migrate

  1. Create a Neon project. Copy both connection strings.

  2. Append these params to the pooled string only:

    ?sslmode=require&pgbouncer=true&connection_limit=1

    Each serverless invocation opens its own pool. Without the cap you exhaust Neon's connection limit under very little traffic.

Why two

The VM worker is one long-running process that manages its own pool, so it uses the direct URL — routing it through PgBouncer buys nothing and costs you prepared statements. Migrations need a real session for advisory locks and DDL, which PgBouncer in transaction mode can't give them. Prisma won't fall back if DIRECT_URL is missing; it hard-errors.

Expected in the logs

CRON_SECRET is not set — /api/cron/* will reject every call. Correct here. Those endpoints are the no-VM fallback; the VM worker owns the recurring work in this setup.

A Prisma "Update available 5.22.0 → 7.9.1" box also appears. Cosmetic — the build already succeeded by the time it prints. Don't take a major version bump mid-deploy.

If the build fails on the output directory

Error: No Output Directory named "public" found… or Error: The Output Directory "public" is empty.

Defining any buildCommand makes Vercel look for static output afterwards, and this build produces none — it only generates the Prisma client and migrates. Vercel rejects a missing directory and an empty one, so the repo commits server/public/index.html to satisfy it.

Confirm that file exists and isn't ignored, and that server/vercel.json has "outputDirectory": "public".

It isn't dead weight: Vercel checks the filesystem before applying rewrites, so it's what you get at the API domain's root, while every other path falls through to api/index.ts.

Why unset beats empty

Leaving WORKER_MODE and REDIS_URL unset is what keeps the function free of Redis. shared/redis.ts builds its client lazily and every queues.ts export no-ops, so a cold start never opens a socket it has no use for.

03 Vercel dashboard

Vercel — client project

Second project, same repo, Root Directory client, name sheetwatch.

VariableValue
VITE_API_BASE_URLempty string
VITE_VAPID_PUBLIC_KEYbyte-identical to the API's VAPID_PUBLIC_KEY

  1. Create the project, Root Directory client, name sheetwatch.

  2. Set both variables, then deploy.

Costly mistake #2 — do not "simplify" this

VITE_API_BASE_URL is empty on purpose. client/vercel.json proxies /api, /auth and /public to the API, so the browser only ever talks to its own origin.

The session cookie is set by the API. Point the client straight at sheetwatch-api.vercel.app and that cookie becomes a third-party cookie — which Safari blocks outright. Sign-in then fails on macOS Safari and on every iPhone, which is exactly where the PWA install matters, since it's the only way web push works on iOS at all.

It will look fine in your Chrome. That's what makes it expensive.

Note

Vite inlines both variables at build time. Changing either needs a redeploy, not just an env edit.

04 Google Cloud console

Google Cloud

  1. APIs & Services → Credentials → your OAuth client. Set the authorized redirect URI to:

    https://sheetwatch.vercel.app/auth/google/callback

  2. Confirm it matches GOOGLE_REDIRECT_URI on the API character-for-character. Google rejects the token exchange otherwise.

  3. Add your own Google account under Test users on the consent screen.

The client origin, not the API's

Google redirects the browser, and the browser has to land on the origin that owns the cookie. The proxy forwards it to the API from there.

Testing mode tradeoff

Keeping the consent screen in Testing needs no Google verification, but refresh tokens expire after roughly 7 days of inactivity — sheets start showing "Access denied — re-authorize in the app." Publishing removes that, at the cost of Google's review.

05 SSH — Hetzner VM

Hetzner VM — worker + Redis

This is where all the recurring work lives: polling, notifying, the compare sweep, digests and reports. Two containers, started with one command.

  1. Clone the repo and prepare the env file:

    git clone https://github.com/prem-raichura/SheetWatch.git
cd SheetWatch/server
cp .env.example .env.production
$EDITOR .env.production

  2. Fill .env.production with the same values as the Vercel API, changing only these three:

    VariableVM valueWhy
    DATABASE_URLNeon direct URLlong-running process, manages its own pool
    WORKER_MODEbullmqselects the queue-backed path
    REDIS_URLignoredcompose overrides it to redis://redis:6379

    SESSION_SECRET and GOOGLE_REDIRECT_URI are unused by the worker but still required by env.ts, which validates one shared list. Copy them across anyway.

  3. Build and start:

    docker compose up -d --build
docker compose logs -f worker

    Scheduled 8 sheet poll job(s)

    Worker started — poll + notify + compare workers running

Networking — do nothing

Neither container publishes a port. Redis is reachable only on the compose network under the hostname redis, and the worker makes outbound connections only. The VM needs no inbound firewall rule beyond SSH. Don't add one.

How the VM learns about changes you make in the UI

The Vercel API has no Redis connection, so it can't schedule jobs. The worker re-derives everything from the database itself, every 60 seconds:

  • sheet added → scheduler created
  • sheet paused, archived or deleted → scheduler pruned
  • pollInterval edited → scheduler retimed

It only writes when something actually differs, so it never churns a scheduler or pushes back its next run. A new sheet starts polling within a minute. Redis losing its data is survivable for the same reason — the next reconcile rebuilds every schedule.

Updating later

git pull && docker compose up -d --build

Schema changes are applied by the Vercel API build, not here. To migrate from the VM instead: docker compose run --rm worker npx prisma migrate deploy

06 Optional · Cloudflare

Realtime worker

Without this the app polls every 30s. With it, changes appear instantly — live bell, toast, list refresh — and the header badge reads live. Nothing else depends on it. 

  1. cd realtime
npm install
npx wrangler deploy
npx wrangler secret put REALTIME_SECRET   # from phase 00

  2. Set REALTIME_URL (the deployed https://…workers.dev origin) and REALTIME_SECRET on both the Vercel API and the VM worker. Redeploy both.

    The API mints the browser's token; the worker publishes the events. Miss either side and it silently stays on polling.

No client variable needed

The client discovers the URL from GET /api/realtime/token. The WebSocket goes browser → Cloudflare directly, authenticated by a 120s HMAC token, so it's unaffected by the cookie proxy arrangement.

Alternative: no VM

To drop the VM entirely, the same work runs from any external scheduler — Upstash QStash, cron-job.org, a crontab anywhere. Leave the API's WORKER_MODE and REDIS_URL unset (they already are), set CRON_SECRET, and schedule both endpoints.

PathSuggested cron
PollPOST /api/cron/poll*/5 * * * *
MaintenancePOST /api/cron/maintenance*/15 * * * *
 
curl -X POST https://sheetwatch-api.vercel.app/api/cron/poll \
  -H "Authorization: Bearer $CRON_SECRET"
# {"due":3,"checked":3,"skipped":0,"changed":1,"failed":0}
Schedule both or things silently stop

/poll only polls sheets. Digests, scheduled reports, snapshot pruning, the quiet-hours flush and the compare sweep all live on /maintenance. Miss it and change notifications keep working perfectly while everything else quietly dies — which is why it can go unnoticed for weeks.

What you give up

  • pollInterval rounds up to the cron tick — a 180s sheet on a */5 schedule is checked every 5 minutes.
  • Every run is capped at the 60s function limit.
  • On QStash's free tier (500 messages/day), */5 + */15 is 384/day. A 1-minute poll would be 1536/day and needs pay-as-you-go.
Overlap is handled

/api/cron/poll claims each sheet with a compare-and-swap on lastCheckedAt before polling, so two overlapping runs can't both poll one sheet and raise duplicate notifications. The loser is reported under skipped — non-zero there means your schedule is tighter than a run actually takes.
